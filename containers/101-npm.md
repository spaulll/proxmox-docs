# CT 101, Nginx Proxy Manager

CT 101 is the reverse proxy and SSL manager for the lab. It is the only container whose service is
referred to by almost everything else: the `.myownserv.duckdns.org` names point to it, the `npm` tag in
the PVE config is the only tag that describes its role, and the proxy-host files under `/data/nginx/`
are where I can see what services it exposes without reading the host-level docs.

The container uses `/etc/resolv.conf` with `nameserver 10.10.10.1`, the OpenWrt router. It is the
first container to start, and it is included in the weekly B2 backup (`597 MB` archive on 2026-10-25).

Memory at capture: 22 MB used out of 512 MB, with 46 MB in buffers and a 489 MB available headroom. The
node process used a peak of 175 MB; nginx processes used about 11 tasks in total. Load average was 0.55.
Swap was 66 MB used. Memory is not tight.

## What runs inside

Systemd services active at capture:

| Service | Unit file | Description |
|---|---|---|
| `npm.service` | `/usr/lib/systemd/system/npm.service` | Node admin process on port `3000` |
| `openresty.service` | `/usr/lib/systemd/system/openresty.service` | Nginx/OpenResty web server |
| `ssh.service` | `/usr/lib/systemd/system/ssh.service` | SSH on port 22 |
| `postfix.service` | local mail transport |
| `cron.service` | `/etc/init.d/cron` |
| `systemd-networkd.service` | container network |

The `npm` node process (`node index.js --abort_on_uncaught_exception --max_old_space_size=250`) runs
with a 250 MB max space limit. It runs continuously and writes to `/data/logs/`. `openresty` listens
on ports 80, 81 and 443. The `81` port is the admin web interface (`production.conf`); `443` is the SSL
proxy endpoint for the hosts.

The container also runs `postfix` (port 25 localhost) and `cron`. The `cron.service` log shows no errors,
but no scheduled tasks were visible inside the container's `cron` files (
`/etc/cron.d` and `/etc/crontabs` are mostly empty). The `npm` service does its own SSL renewal schedule:
it calls `/etc/letsencrypt/live/npm-2/` for certificates and logs renewals every hour (`SSL Renewing` at
14:25, 15:56, 16:56, 17:56, 18:56, 19:56). The certificate files are symlinks to `/data/letsencrypt/`.

Port 3000 (`node`) is the Nginx Proxy Manager admin API; the `production.conf` proxies `/api/` through it.
Port 80 serves the proxy-host rules; port 81 serves the admin UI (`root /app/frontend`); port 443 handles
SSL for proxy hosts and rejects the default SSL handshake with 444 when the host is `localhost`.

There is a `fallback_access.log` and `fallback_error.log` under `/data/logs/`. They are empty at capture
but rotated by logrotate rules. There is no `/etc/nginx/proxy_host/` directory inside the container; all
proxy-host rules come from `/data/nginx/proxy_host/*.conf`.

## Network and ports

| Port | Process | Purpose |
|---|---|---|
| 80/tcp | `nginx` (openresty) | proxy hosts |
| 81/tcp | `nginx` | admin UI |
| 443/tcp | `nginx` | SSL proxy hosts |
| 3000/tcp | `node` (npm) | admin API |
| 22/tcp | `sshd` | SSH access |

The admin UI (`production.conf`) listens on 81, not 443; 443 is only for proxy-host SSL, with the
admin interface protected by being on 81 and requiring a login through `/api/`.

The container receives `net0` from `vmbr1`, same as CT 106 and the lab guests. It uses `nameserver: 10.10.10.1`
and `nameserver 192.168.0.147` in `/etc/resolv.conf`. It uses DHCP; the lease renews regularly with a
valid lifetime of about 12 hours (seen 31603 sec at capture).

The container's `/etc/network/interfaces` is not visible inside (managed by `systemd-networkd`). The host
sets the `nameserver` to `10.10.10.1`, which means the proxy manager resolves names through the lab router.
That is consistent with OpenWrt's `dnsmasq` forwarding to AdGuard.

## Proxy hosts (what I can see)

The proxy-host directory (`/data/nginx/proxy_host/`) has 15 `.conf` files. I read the header lines for
a few of them to confirm their names without copying the upstream details. There are proxy hosts for:

- `npm.myownserv.duckdns.org` -> `10.10.10.200:81` (this container's own admin interface, via `proxy_host/1.conf`)
- `jellyfin.myownserv.duckdns.org` -> `10.10.10.201:8096`
- `immich.myownserv.duckdns.org` -> `10.10.10.234:2283`
- `prox.myownserv.duckdns.org` -> `192.168.0.50:8006` (Proxmox UI, HTTPS upstream)
- `asus.lan` -> `192.168.0.1:8443`

These are only the ones I inspected from the config headers. There are 15 proxy-host files total, which
matches the number of services mentioned in `README.md` (`proxy` references `10.10.10.200`; other services
have their own upstream ports). I have not listed the rest, and I have not looked at the SSL certificate
values or auth tokens inside the proxy-host database (`/data/nginx/proxy_host/*.conf` contains no
credentials, but `/data/nginx/custom/` or `/etc/nginx/conf.d/` might). The `include/proxy.conf` shows the
proxy-passing logic; it includes `proxy_set_header` for `X-Real-IP`, `Host`, `X-Forwarded-Scheme` and
`X-Forwarded-Proto`, which is standard.

The admin web UI (`/api/`) uses port 3000 and a redirect to `/`. The `node` process is started by
`npm.service`; `ExecStart=/usr/bin/node index.js --abort_on_uncaught_exception --max_old_space_size=250`.

Logs rotate weekly; the `proxy-host-28_access.log` is 285 kB, `proxy-host-6_access.log` is 7.3 MB. There
is no `proxy-host-20_access.log`. The logs contain only HTTP request lines; no secrets appear. The
`proxy.conf` rules include `real_ip_header X-Real-IP`, `proxy_set_header X-Real-IP $remote_addr`, so the
upstreams see the client's original IP.

## SSL

The NPM manages SSL certificates through `npm.service`. The `/etc/letsencrypt/live/npm-2/` directory
contains symlinks to the archive (`cert7.pem`, `fullchain7.pem`, `privkey7.pem`, `chain7.pem`). A custom
certificate exists at `/data/custom_ssl/npm-3/` (`fullchain.pem`, `privkey.pem`). The `proxy_host/1.conf`
references `/etc/letsencrypt/live/npm-2/fullchain.pem`; `proxy_host/10.conf` references the custom SSL
path. The `ssl-ciphers.conf` includes standard cipher settings.

The `npm.service` log shows `Renewing SSL certs expiring within 30 days` running hourly. The last renewal
before capture was at 19:56 on 2026-10-31, with `Completed SSL cert renew process` immediately after.
The certificate (symlink target `cert7.pem`) was issued for `npm-2`; the custom SSL (`npm-3`) is separate.

Certificates are stored inside the container filesystem (`/etc/letsencrypt/` and `/data/custom_ssl/`).
Restoring the container from B2 restores these paths.

## Data

`/etc/nginx/` holds the static nginx/openresty configuration. `/data/nginx/` holds the dynamic rules,
proxy hosts, redirection hosts, dead hosts, temp files, stream configs; `proxy_host/` has 15 `.conf`
files; `default_host/` is empty; `redirection_host/` is empty. `/data/custom_ssl/npm-3/` holds one custom
cert. `/data/logs/` holds the access and error logs.

No bind mounts. The container's root filesystem (3.9 GB) includes all of this. The weekly B2 backup
includes the 4 GB root filesystem; the archive for 2026-10-25 was 597 MB.

The NPM admin interface (`node` process) does not use bind mounts. Its state is in `/data/nginx/` and
`/etc/letsencrypt/`. If the container is rebuilt, the NPM config and certificates are rebuilt from the
archive, but the upstream proxy rules (hostnames, ports) would need to be verified afterward.

## Health

The `npm` node service started 4 days before capture (`Active: active (running) since Tue 2026-10-27`).
`openresty` started about one minute later. The container has been running continuously.

`systemctl --no-pager` shows `npm.service` and `openresty.service` active. `systemctl status` shows no
failures; the `npm.service` log shows only SSL renewals. `postfix.service` is active with no errors
(`mail.log` is empty or very small). No recent errors in `/data/logs/fallback_error.log` (only old
rotated `.gz` files). The `proxy-host-*_access.log` files grow continuously but are rotated.

No firewall rules or `nft` ruleset were visible inside this container; the firewall is handled by the host
and OpenWrt, not by NPM. The `openresty.service` runs as root (the nginx master); `npm.service` runs as
user `npm`. The container is `unprivileged` on PVE (`unprivileged: 1`) with `nesting=1` and `keyctl=1`.

The `nginx.conf` includes a custom root-top conf (`/data/nginx/custom/root_top[.]conf`) and a custom
stream conf (`stream[.]conf`). I did not inspect those custom files. The `proxy.conf` and `ssl-ciphers.conf`
are standard.

## Recovery

The container is backed up weekly. Restoring it brings back nginx/openresty config, NPM database, SSL
certificates and proxy-host rules. After restore:

- verify the `npm.service` starts (`systemctl status npm openresty`)
- verify the proxy-host rules load by checking `nginx -t` or `systemctl status openresty`
- confirm the admin web (`curl -k https://npm:81/`) and the proxy hosts (`curl -k https://npm.myownserv.duckdns.org/`)
- review SSL renewal (`systemctl status npm` or `/etc/letsencrypt/live/npm-2/`)

The NPM admin interface requires a login; the credentials are not stored in this repo and are not
reproduced here. The proxy-host rules reference upstream ports (`10.10.10.200:81`, `192.168.0.1:8443`, etc.)
but do not include authentication details.
