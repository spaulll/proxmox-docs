# CT 105, NAS

A small Alpine container that shares the data disk over Samba and NFS. It's the door to `/mnt/data` for the rest of the LAN.

## Identity and resources

| | |
|---|---|
| Hostname | `NAS` |
| Proxmox ID | 105 |
| OS | Alpine Linux 3.22.5 |
| CPU / RAM / swap | 1 vCPU, 512 MB RAM, 512 MB swap |
| Disk | 2 GB thin volume, 307 MB used (17 %) |
| Address | `192.168.0.10/24`, gateway `192.168.0.1` |
| DNS | `192.168.0.147` (AdGuard VIP) |
| Startup | `onboot: 1`, order 3 |
| Type | unprivileged |
| Backup | weekly B2 job (rootfs only) |

The container itself is tiny — 2 GB root filesystem, 307 MB used. The real payload is the bind mount: `/mnt/data` (the USB sdb disk) appears at `/srv/samba`, exported over Samba and NFS. That's a `noatime` ext4 mount showing 305 GB used of 468 GB.

Uptime at inspection: 5 days 21 hours, load 0.18. Memory 512 MB limit, plenty free. The host's 16 GB shows through in `free` because of the container's cgroup view, same quirk as CT 106.

## What runs inside

Alpine OpenRC services, all started at default runlevel:

| Service | What it does |
|---|---|
| `samba` | smbd + nmbd, shares `public` and `private` |
| `unfs3` | NFSv3 server (unfsd), exports the same two paths |
| `rpcbind` | required by NFS |
| `sshd` | SSH (Alpine's, on 22) |
| `crond` | periodic maintenance |
| `networking` / `localmount` | network + mount plumbing |

Notable: `syslogd` runs, no firewall service is present at all — this container is wide open on the LAN. That matches the "trusted LAN" posture, and the shares themselves carry the access control.

## Samba

Config is `/etc/samba/smb.conf`. Global settings:

- workgroup `WORKGROUP`, netbios name `SAMBA-NAS`
- `security = user`, `map to guest = bad user`
- binds only to `192.168.0.10/24` on `eth0` (`interfaces` + `bind interfaces only = yes`)
- `wins support = yes`, name resolve order host bcast
- SMB2 minimum, SMB3 maximum, signing disabled both ways

Two shares:

| Share | Path | Read | Write access |
|---|---|---|---|
| `public` | `/srv/samba/public` | guest ok (yes) | `write list = root lobstr`, forced user/group root |
| `private` | `/srv/samba/private` | `valid users = root lobstr` | `admin users = root lobstr`, read-only no |

Both have the recycle VFS object — deleted files go to a `.recycle` per share, keeping the tree and versions. `private` also sets `recycle:directory_mode = 0700`.

Users are `root` and `lobstr`. The Samba password database lives in the container and is not recorded here. The `smb.conf` history shows several backups (`pre-root-fix`, `apk-new`, `.bk`, `.lobstr`, `.nobody`) — the config's been hand-edited a few times, and the backups are kept. No clients were connected at inspection (`smbstatus -S` empty).

## NFS

`unfs3` (userland NFSv3) runs as user `paul`, serving on 2049. `/etc/exports`:

```
/srv/samba/public   192.168.0.0/24(rw,no_root_squash)
/srv/samba/private  192.168.0.0/24(rw,no_root_squash)
```

Both are rw to the whole LAN with no root squash. Between that and the open firewall, the `private` path is only guarded by Samba's user check — NFS itself treats it as rw to anyone on the subnet. Accepted as-is on this trusted LAN. NFS is the path used from a Linux laptop; SMB is used from Android — both are in regular use.

## Data

Everything under `/srv/samba/` is the bind mount of host `/mnt/data`. Contents:

- `public/` — Downloads, immich, backups, syncthing
- `private/` — 6.4 GB, owned by nobody/nobody, not shared with other containers

None of it lives in the container's root filesystem.

## Backup

CT 105 is in the weekly B2 job — archive was 76 MB on 2026-10-25. That backs up the small Alpine rootfs only. The actual shared data is a bind mount, so it is **not** in the archive. The shares are a window onto `/mnt/data`, not a store of their own.

## Health

## What happens if something fails

| Failure | Effect |
|---|---|
| CT 105 stops | SMB/NFS shares disappear for the LAN. The data itself is safe on `/mnt/data`. |
| `/dev/sdb` drops | The bind mount goes away; container may report the mount as gone. Host uses `nofail` so it still boots. |
| Share permissions break | `public` is forced root/root, so writes work regardless — that masks permission problems rather than fixing them. |

## Recovery

Restore rootfs from B2, start, verify the mount and both exports. The 76 MB archive is the config, not the data.

```bash
pct restore 105 /mnt/data/restore/nas-105-<timestamp>.tar.zst --storage local-lvm
pct start 105
```

Checks:

```bash
pct exec 105 -- rc-status
pct exec 105 -- smbstatus -S
pct exec 105 -- cat /etc/exports
pct exec 105 -- ls /srv/samba
```
